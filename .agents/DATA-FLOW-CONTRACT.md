# Data-flow handshake

The `data-contract-checker` owns this contract. Feature agents propose changes; the checker updates and verifies the shared contract in the same pull request.

## Boundary map

The profile prerequisite is checked when the worker creates `MATCH_PROFILE_EVIDENCE` task identity. A blocked task preserves its task/attempt history and is recoverable only after the repair path confirms exactly one active profile and verifies that every eligible current profile fact has a published embedding in the configured primary space. The repair path clears the dependency metadata and requeues only tasks with the matching `blocked_on` and `repair_action` values. It does not write a gate, lane, match, or recommendation outcome. These values use the existing `pipeline_tasks` dependency fields and `BLOCKED_DEPENDENCY` status; they do not change the task-intent payload contract or the database shape.

Pipeline task queue age: pending age is measured from when a task became due, `GREATEST(created_at, available_at)` over PENDING tasks with `available_at <= NOW()` (`v_pipeline_task_due_age`, migration 107); retry age is measured from entry into `RETRY_WAIT` (`updated_at`, `v_pipeline_task_status_age`, migration 099). Moving a task back to PENDING (dependency unblock, dead-letter replay) sets `available_at = NOW()` and so resets its due age; time spent `BLOCKED_DEPENDENCY` is reported separately. PENDING tasks scheduled for later are excluded from the pending-age SLO and from the worker's no-forward-progress rule, which counts only due PENDING tasks, but they are still reported: `scheduled_pending` and `latest_scheduled_available_at` in the worker output and `scheduled_pending` per stage in `scripts/report_pipeline_status.ts`. `scripts/process_pipeline_tasks.ts` and `scripts/run_scoped_pilot.ts` use the same metrics.

Availability policy details:

- Any retrieved posting with `description.completeness_status=COMPLETE` has a seven-day `OPEN` availability window, regardless of source. Greenhouse, Lever, Ashby and Workday use their adapter source identity (the employer's own ATS) to establish retrieval; Gmail-derived postings still require the complete, lineage-bound fetch receipt, and non-ATS boards still require an exact pinned-manifest host. Incomplete ATS listings may remain `OPEN` from the ATS listing status but keep the one-day window; alert-only and unverified listings remain `UNKNOWN`.
- Source-plugin schema `2.3.0` accepts up to 20 exact DNS hostnames per manifest. Host comparison is case-insensitive and may normalize one trailing dot; it must not accept wildcard entries or an unlisted subdomain. The source URL must be credential-free HTTP(S). The configured hosts are `himalayas.app` and `www.himalayas.app`, `jobicy.com` and `www.jobicy.com`, `weworkremotely.com` and `www.weworkremotely.com`, and `news.ycombinator.com` (Hacker News comment URLs).
- A Gmail-derived posting may become `OPEN` only when its complete posting carries a schema-valid receipt (`requestedUrl`, `resolvedUrl`, `redirectHistory`, `retrievedAt`, `httpStatus`, `contentType`, and `responseHash`), `derived_from_observation_id` identifies a `GMAIL_ALERT` observation, and the payload `discovery_observation_id` equals that exact parent ID. Root `requested_url`, receipt `requestedUrl`, and the parent's discovered URL must match exactly. `resolvedUrl` records the final transport endpoint and is independently validated as a credential-free HTTP(S) URL; ATS APIs may serve a posting through a different endpoint from its employer-facing canonical URL. Root `canonical_url` and `posting.canonicalUrl` must match the fetched posting observation URL exactly. Receipt posting `companyName`, `title`, and `description` must match the persisted child observation fields exactly. A valid-looking receipt on its own is not lineage proof.
- A saved-export (or other pre-staging) explicit source status is verified as of its `availability_checked_at`, not the staging time, with the one-day explicit-status window (`EXPLICIT_SOURCE_STATUS`); a check time that is not an ISO timestamp, or is more than five minutes after the observation's retrieval, leaves the status `UNKNOWN`. Dates converted from relative text are approximate, never authoritative: the stored value is the newest possible date, the evidence keeps `basis=PUBLISHED_AT`/`GENUINE_REPOST_AT` with a LOW-confidence span and `dates.*.approximation` (`precision`, `earliest_value` one unit earlier, `source_text`, `anchor_at`), normalization writes `job_versions.freshness_basis` as `POSTED_AT_APPROXIMATE_<UNIT>` / `REPOSTED_AT_APPROXIMATE_<UNIT>` with `freshness_confidence=50`, and `evaluateJobFreshness` (gate, decider, ranking) returns a LOW-confidence approximate basis: within the posting-age limit only when the oldest possible date is, `STALE` only when the newest is past it, and `UNKNOWN` (readiness `NEEDS_VERIFICATION`, no hard rejection) when the range straddles the limit; a STALE verdict at MONTH/YEAR precision (unconfirmed rounding) does not hard-reject; a posting date more than a day after the assessment is unknown age. The basis travels with its date: when normalization fills an empty `source_published_at` on an existing version (including a `NEW_POSTING_ID` version enriched later) it writes the date's own, possibly approximate, basis and confidence, and a repost basis changes only with a newer repost date. The decider also reads the approximation from the latest source evidence when its value equals the stored date, whatever the version's basis. `freshness_basis` values are documented by `FRESHNESS_BASIS_PATTERN` (`NEW_POSTING_ID`, `NO_DATE`, `UNKNOWN`, `POSTED_AT`, `REPOSTED_AT`, and `<POSTED_AT|REPOSTED_AT>_APPROXIMATE_<MINUTE|HOUR|DAY|WEEK|MONTH|YEAR>`); `parseFreshnessBasis` is fail-safe, so any other value is `UNRECOGNIZED` and gives unknown age, never an authoritative date. Root posting facts and `date_derivations` are parsed against `PostingFactsPayloadSchema` (`src/contracts/postingFacts.ts`); a malformed set, or a derivation anchored after the observation's retrieval, quarantines the observation's normalized evidence (error recorded) instead of being read in part. Relative text is anchored only to `postingCheckedAt`, never to `exportedAt`; a check time after the import is not used. The export snippets read the closed banner, age text and apply control only from the posting's own top card, and a `refresh()` re-read that fails keeps the earlier facts with their original check time and records `postingRecheckFailedAt` / `postingRecheckFailure`. SearchAPI `linkedin_job_details` `posted_at` text is converted the same way against the response time (`posting.date_derivations.publishedAt`); its repost labels stay unknown.
- Manual source provenance records the origin and editing history of the submitted content. It does not infer `OPEN`: a fetch receipt establishes content retrieval and identity, not current availability; pasted/uploaded `MANUAL_STREAMLIT` postings remain `UNKNOWN` unless an existing independent availability source (such as an explicit source status or employer ATS listing) verifies them. User confirmation and content completeness alone are not availability evidence.
- Evidence refresh uses the observation's pinned plugin revision and exact job-version lineage, preserves a baseline before replacing observation evidence, and recomputes readiness after persistence. A refreshed `OPEN` or `CLOSED` value updates the version projection; an `UNKNOWN` refresh does not overwrite the previous projected status, but the latest normalized evidence takes precedence for readiness, and any `OPEN` result is usable only through its expiry time.
- Emit `job_source_evidence_v2` when `verification_method=VERIFIED_POSTING_RETRIEVAL`, while keeping v1 records readable. Runtime readers, PostgreSQL version constraints, and SQL readiness/read-model consumers must accept both versions; update database constraints additively in the same change as a new emitted version, and regenerate the exported schemas for both versions and their parent contracts.
